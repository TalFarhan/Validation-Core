ארבעת ה-KPI

KPI ב-UI מקור DB כלל עיקרי
סה״כ רכבים שנקלטו [DIM].[Vehicle] Environment = מבצעי
סה״כ רכבים בשימוש [DIM].[Vehicle] IsActive = 1 + Environment
רכבים שזוכו [FACT].[SigningReturnVehicle] סינון דרך DIM (VehicleID) + Environment
רכבים שווסתו [FACT].[VehicleFlow] סינון דרך DIM (VehicleID) + Environment
פילטרים משותפים: Unit / SubUnit / VehicleCategory / VehicleSource — כמו ב-Power BI (דרך DIM).

שלמות נתונים ומקרי קצה

אינווריאנטים עסקיים — 8

  • בשימוש ≤ סה״כ (UI + DB)
  • זוכו נספר מ-FACT SigningReturnVehicle
  • שווסתו נספר מ-FACT VehicleFlow
  • סכום פילוח מקור = KPI בשימוש
  • סכום פילוח יחידה = KPI בשימוש
  • סכום פילוח קטגוריה = KPI סה״כ
  • סכום סיבות זיכוי = KPI שזוכו

מקרי קצה — 6

  • סינון עם אפס תוצאות → KPI = 0
  • ניקוי סינונים מחזיר ל-baseline מול DB
  • רענון דף משחזר ערכי בסיס
  • סינון קיצוני מצמצם את כל ארבעת ה-KPI
  • אימות FACT ל-KPI זוכו / שווסתו

ערך עסקי

מה הרווחנו

  • אמון בנתונים — המספרים בדשבורד ניתנים לאימות מול המחסן בכל הרצה
  • רגרסיה חוזרת — אחרי שינוי BI/Data אפשר להריץ suite מלא במקום סבב ידני חלקי
  • שפה משותפת — קטלוג כיסוי אחד ל-BI, Data ו-Validation
  • ראיה לתיעוד — CSV בעברית לכל ריצה (מה נבדק, מה עבר/נכשל)
  • גילוי מוקדם — פערים בטולטיפ, הסתעפות, או אינווריאנט נתפסים לפני מסירה
המלצה

שלבים הבאים (מוצע)

1 · יציבות מקומית

המשך הרצות sanity/regression לפני כל שינוי בדשבורד; שמירת CSV כראיה.

2 · Auth צוותי

הסכמה על service account או תהליך חידוש מבוקר של סשן הפורטל.

3 · CI + פרסום

Pipeline שמריץ, מייצר Allure/CSV, ומפרסם דוח למקום קבוע.

בלי שלבים 2–3 הכלי עובד מקומית; עם CI הוא הופך לחלק מתהליך המסירה הארגוני.
